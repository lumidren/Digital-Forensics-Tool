# Veritas DFIR — Threat Model

Status: living document. Every mitigation row names the file and line that implements the
control. `scripts/check_threat_model.py` runs in CI and fails if a referenced file does not
exist or no longer carries the matching `THREAT:<id>` marker, so the table cannot drift from
the code silently. Line numbers in this file are regenerated by `scripts/check_threat_model.py --update`.

## 1. Scope and assets

| Asset | Why it matters |
|---|---|
| A1 Evidence objects (images, memory, triage bundles) | Loss or alteration destroys the case. |
| A2 Custody ledger | The only thing that lets an examiner prove A1 is what was seized. |
| A3 Examiner signing keys (Ed25519) | Forged entries would be indistinguishable from real ones. |
| A4 Parsed artifacts and timeline | Analytical conclusions and findings rest on them. |
| A5 Case metadata, notes, hypotheses, findings | Work product, often privileged. |
| A6 Audit log | Required to answer "who looked at what, when". |
| A7 Platform secrets (DB credentials, KMS, OIDC client secrets) | Pivot point for everything else. |
| A8 Build pipeline and release artifacts | Tampered binaries undermine every other control. |

## 2. Actors

| Actor | Capability | Motivation |
|---|---|---|
| Insider examiner | Authenticated, has case access, may have local admin on a workstation. | Alter evidence, hide activity, plant artifacts, exfiltrate PII. |
| Compromised examiner account | Same as above, remotely driven. | Same, plus destruction. |
| Subject of investigation | Controls content of the evidence before acquisition. | Crash or exploit parsers, inject false timeline events, anti-forensics. |
| Network attacker | Observes and tampers with traffic between agent and server. | Intercept images, replay or alter uploads. |
| Platform operator | Root on hosts, access to object store and database. | Silent modification of stored objects or ledger rows. |
| Supply-chain attacker | Publishes a malicious dependency or compromises CI. | Backdoor the agent or the verifier. |

## 3. Trust boundaries

```
[Target host] --agent (Rust, signed)--> mTLS --> [Intake API] --> [Object store, WORM]
                                                        \--> [Ledger (append-only, hash chained)]
[Evidence bytes] --> [Sandboxed parser worker (no network, resource caps)] --> [Timeline index]
[Examiner browser] --OIDC--> [Web API, RBAC] --> [Case DB, Audit log]
[Verifier CLI] <-- custody export (signed JSON); needs only public keys, no platform access
```

The verifier CLI sits outside every other boundary. It depends on nothing but the exported
ledger and the public keys, so a court-appointed expert can run it on an air-gapped laptop.

## 4. Threats and mitigations

Marker convention: the implementing line carries a comment `THREAT:<id>` so the checker can
confirm the reference. Where a threat has several mitigations each has its own row.

### T1 Evidence tampering after acquisition (insider or platform operator)

| # | Mitigation | Location |
|---|---|---|
| T1.1 | Three independent digests (MD5, SHA-256, SHA3-256) computed in one streaming pass during acquisition, before bytes leave the agent. | crates/veritas-hash/src/lib.rs:23 |
| T1.2 | Object store addresses every blob by SHA-256; a modified blob cannot keep its address. | crates/veritas-store/src/lib.rs:58 |
| T1.3 | Local store marks committed objects read-only and refuses to overwrite an existing address (WORM semantics); the S3 backend requires Object Lock compliance mode. | crates/veritas-store/src/lib.rs:157 |
| T1.4 | Every read of an evidence object appends a signed Access entry to the ledger; silent reads are impossible through the API. | crates/veritas-ledger/src/lib.rs:222 |
| T1.5 | Re-verification command re-hashes stored objects and compares against the acquisition entry. | crates/veritas-cli/src/main.rs:207 |

### T2 Chain-of-custody forgery

| # | Mitigation | Location |
|---|---|---|
| T2.1 | Each entry is Ed25519-signed over its canonical JSON (sorted keys, no floats, no whitespace). | crates/veritas-ledger/src/canonical.rs:24 |
| T2.2 | Each entry embeds the SHA-256 of the previous entry; deleting or reordering an entry breaks every later hash. | crates/veritas-ledger/src/lib.rs:141 |
| T2.3 | Sequence numbers must increase by exactly one; the verifier rejects gaps and duplicates. | crates/veritas-ledger/src/verify.rs:84 |
| T2.4 | A trusted-time record (source identity, measured offset, uncertainty) is captured with each acquisition entry and covered by its signature. | crates/veritas-ledger/src/lib.rs:66 |
| T2.5 | Independent verifier re-validates from scratch and prints PASS or FAIL; it shares only the canonical-form code with the writer. | crates/veritas-ledger/src/bin/veritas-verify.rs:7 |
| T2.6 | Periodic anchoring of the chain head into an external append-only anchor file (RFC 3161 TSA adapter optional). | crates/veritas-ledger/src/anchor.rs:6 |

|---|---|---|

## 5. Residual risks (accepted and documented)

- A platform operator with root on the ledger host and an unlocked examiner key can forge
  entries from that examiner until the next external anchor. Anchoring cadence limits the window.
- Memory acquisition on a compromised kernel can be subverted by a rootkit. The agent records
  the driver hash and kernel version so the limitation is visible in the report.
- The verifier trusts the public-key registry it is given. Out-of-band distribution of the
  registry (fingerprints printed in the custody report) is a procedural control.
